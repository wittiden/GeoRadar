# Контракт данных

Единый формат измерений для всех источников, загрузки CSV и выгрузки. Код-версия контракта: `schemas.py` (Pydantic + хелперы разбора). Если документ и код расходятся, прав код.

Состояние источников: orsha-ecokarta по ответам, присланным в начале октября 2026; rad.org.by по страницам и RSS-фидам, открытым 7 октября 2026. Раздел 4 это снимок: источники могут измениться, поэтому адаптеры должны валидировать ответы и логировать расхождения.

## 0. Источники и охват

На rad.org.by четыре раздела мониторинга (радиация, воздух, поверхностные воды, земли), на orsha-ecokarta пока разобран воздух и выбросы по Орше.

| `source` | Что отдаёт | Откуда | Периодичность | Координаты в данных | Статус |
|---|---|---|---|---|---|
| `rad_rss` | Мощность дозы гамма-излучения, 42 поста | `https://rad.org.by/radiation.xml` (RSS) | раз в сутки, при превышении порога раз в час | нет | разобран |
| `rad_air_rss` | Загрязнители воздуха в долях ПДК, 19 постов | `https://rad.org.by/rss-air-avto.xml` (RSS) | непрерывные измерения; ТЧ за предыдущие сутки | нет | разобран, см. раздел 8 |
| `rad_ikav_rss` | Индекс качества воздуха (ИКАВ), 13 постов | `https://rad.org.by/rss-air-ikv.xml` (RSS) | ежечасно | нет | разобран |
| `rad_water_rss` | Классы качества поверхностных вод, более 100 пунктов | `https://rad.org.by/rss-water.xml` (RSS) | раз в год | нет | разобран |
| *(резерв)* `rad_soil` | Загрязнение земель (почв) | `https://rad.org.by/monitoring/soil.html` | раз в 5 лет на пункт | не проверено | машиночитаемый источник не найден |
| `orsha_ecokarta` | Воздух (посты) и выбросы предприятий, г. Орша | `https://orsha-ecokarta.gov.by/api/*` (JSON) | сутки или месяц | да | воздух и выбросы разобраны |
| `upload` | Данные, загруженные пользователем из CSV (раздел 5) | файл | любая | в файле | служебный источник |
| *(не изучено)* | Воды, почвы и радиация на orsha-ecokarta | страницы разделов | неизвестно | неизвестно | не смотрели |

Все материалы rad.org.by разрешено использовать только со ссылкой на сайт: `source_url` для источников `rad_*` обязателен.

## 1. Модель

Три сущности: **станция** (пост, предприятие, пункт наблюдений), **параметр** (что измеряем), **измерение** (значение параметра на станции за период времени).

### Станция (`StationIn`)

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `source` | str | да | Код источника из раздела 0 |
| `external_id` | str | да | Идентификатор в источнике (правила для каждого источника в разделе 4) |
| `name` | str | да | Название. Лишние пробелы и переводы строк убираются |
| `kind` | enum | нет | `air_post`, `industrial_site`, `radiation_post`, `water_post`, `soil_point`, `other` (по умолчанию `other`) |
| `address` | str | нет | Адрес, если источник его отдаёт |
| `lat` | float | да | Широта, WGS84, десятичные градусы, 51.0–56.5 |
| `lon` | float | да | Долгота, WGS84, десятичные градусы, 23.0–33.0 |
| `geo_quality` | enum | да | `source` (координаты из источника), `geocoded` (геокодинг по названию), `manual` (справочник вручную) |

Станция уникальна по `(source, external_id)`. Один физический пост в разных источниках (например, воздух в `rad_air_rss` и в `rad_ikav_rss`) это разные станции: автоматически мы их не склеиваем.

### Измерение (`MeasurementIn`)

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `station` | StationIn | да | Станция |
| `parameter` | str | да | Код параметра из справочника (раздел 3), `[a-z0-9_]+` |
| `parameter_name` | str | нет | Название параметра. Используется, только если параметра ещё нет в справочнике (автосоздание) |
| `value` | decimal | да | Число, десятичный разделитель точка. NaN и бесконечности отклоняются |
| `unit` | str | да | Каноническая единица: `uSv/h`, `ug/m3`, `mg/dm3`, `pdk_ratio` (доли ПДК), `class` (порядковый класс) |
| `measured_at` | datetime | да | **Начало** периода измерения, ISO 8601. В БД хранится в UTC |
| `period_kind` | enum | нет | `instant` (по умолчанию), `day`, `month`, `year`: за какой промежуток значение |
| `pdk` | decimal | нет | ПДК или норматив, **как указан в источнике** рядом со значением |
| `sub_point` | str | нет | Доп. ключ ряда внутри станции (напр. номер источника выбросов). Пустая строка = нет |
| `sub_point_name` | str | нет | Человекочитаемое название `sub_point` |
| `source_url` | str | нет | Откуда взято (для `rad_*` обязательно) |
| `raw` | object | нет | Исходная запись источника, для отладки |

Измерение уникально по `(станция, parameter, sub_point, measured_at)`. Повторная загрузка тех же данных дублей не создаёт.

## 2. Правила

- **Время.** ISO 8601, например `2026-10-03T18:00:00+03:00`. Без часового пояса считаем `Europe/Minsk` (UTC+3, без перехода на летнее время). В БД всё в UTC, **в CSV-выгрузке и в API время выводится в Минске** (`+03:00`), чтобы суточное значение за 1 октября осталось `2026-10-01T00:00:00+03:00`, а не `2026-09-30T21:00:00Z`. Даты в RSS (`Thu, 27 Aug 2026 17:20:00 +0300`) разбирает `email.utils.parsedate_to_datetime`.
- **Период.** У источников разная гранулярность: момент, сутки, месяц, год. `measured_at` это начало периода, `period_kind` говорит, какой он длины.
- **Координаты.** Порядок строго `lat, lon`. Выход за границы Беларуси считается ошибкой (ловит перепутанные оси).
- **Числа.** Точка как разделитель, без пробелов. Пустые и нечисловые значения (`null`, `н/д`) пропускаются и попадают в отчёт об ошибках. Значения вида `<0.01` в тексте не разбираются: если источник даёт рядом числовой тег (rad.org.by, воздух), берём его, а исходный текст сохраняем в `raw`.
- **Единицы.** Одна каноническая единица на параметр, адаптер приводит сам: `мкЗв/ч → uSv/h`, `мкг/м3 → ug/m3`, `мг/дм3 → mg/dm3`, `ПДК → pdk_ratio`, `класс → class`. Неизвестная единица это ошибка строки, а не повод молча пропустить.
- **Порядковые классы** (`class`): целое число, 1 = лучшее состояние. Это не измерение концентрации, поэтому сравнивать с `ug/m3` и `pdk_ratio` нельзя.
- **Ошибки.** Невалидная строка не роняет всю загрузку: она пропускается и попадает в отчёт `(номер строки, поле, причина)`.

## 3. Справочник параметров

Код составляется как «что измеряем + где/в чём». Одно и то же вещество в разных источниках имеет **разные** параметры, потому что отличаются единицы и смысл: концентрация (`ug/m3`) у orsha, доли ПДК (`_pdk`) у rad.org.by, выбросы у предприятий (`emis_`). Склеивать их в один параметр нельзя.

| Код | Что это | Единица | Источник и поле |
|---|---|---|---|
| `gamma_dose_rate` | Мощность дозы гамма-излучения | `uSv/h` | `rad_rss`, `<rad>` |
| `air_so2_pdk` | Серы диоксид, воздух, доли ПДК | `pdk_ratio` | `rad_air_rss`, тег `ing2` |
| `air_co_pdk` | Углерод оксид, воздух, доли ПДК | `pdk_ratio` | `rad_air_rss`, `ing4` |
| `air_no2_pdk` | Азота диоксид, воздух, доли ПДК | `pdk_ratio` | `rad_air_rss`, `ing5` |
| `air_no_pdk` | Азота оксид, воздух, доли ПДК | `pdk_ratio` | `rad_air_rss`, `ing6` |
| `air_o3_pdk` | Приземный озон, доли ПДК | `pdk_ratio` | `rad_air_rss`, `ing7` |
| `air_pm10_pdk` | ТЧ-10, доли ПДК, среднее за предыдущие сутки | `pdk_ratio` | `rad_air_rss`, `ing200` |
| `air_pm25_pdk` | ТЧ-2,5, доли ПДК, среднее за предыдущие сутки | `pdk_ratio` | `rad_air_rss`, `ing203` |
| `air_o_xylene` | О-Ксилол, воздух | `ug/m3` | `rad_air_rss`, `ing46` |
| `ikav_no2` | ИКАВ по азота диоксиду | `class` | `rad_ikav_rss`, `<NO2>` |
| `ikav_co` | ИКАВ по углерод оксиду | `class` | `rad_ikav_rss`, `<CO>` |
| `ikav_so2` | ИКАВ по серы диоксиду | `class` | `rad_ikav_rss`, `<SO2>` |
| `ikav_o3` | ИКАВ по приземному озону | `class` | `rad_ikav_rss`, `<O3>` |
| `water_class_bio` | Класс качества воды по гидробиологическим показателям | `class` | `rad_water_rss`, `<bio>` |
| `water_class_chem` | Класс качества воды по гидрохимическим показателям | `class` | `rad_water_rss`, `<chem>` |
| `air_pm_total` | Твёрдые частицы в воздухе | `ug/m3` | `orsha_ecokarta`, `monitoring_aas_orsha`, pollutant_id `10` |
| `air_co` | Углерод оксид в воздухе | `ug/m3` | `orsha_ecokarta`, pollutant_id `2` |
| `air_no2` | Азота диоксид в воздухе | `ug/m3` | `orsha_ecokarta`, pollutant_id `12` |
| `air_so2` | Серы диоксид в воздухе | `ug/m3` | `orsha_ecokarta`, pollutant_id `4` |
| `emis_pm_total` | Твёрдые частицы, выброс | `mg/dm3` | `orsha_ecokarta`, `ac_air_place_substances`, substance_id `10` |
| `emis_co` | Углерод оксид, выброс | `mg/dm3` | `orsha_ecokarta`, substance_id `201` |
| `emis_no2` | Азот (IV) оксид, выброс | `mg/dm3` | `orsha_ecokarta`, substance_id `84` |

Справочник неполный, новые вещества появятся. **Неизвестное значение не отбрасывается**, параметр создаётся автоматически (адаптер передаёт `parameter_name` и единицу):

- orsha, воздух: `air_p<pollutant_id>`; orsha, выбросы: `emis_p<substance_id>`;
- rad_air_rss, неизвестный тег `ing<N>`: `rad_air_ing<N>`, единица берётся из тега, название из описания.

Источник правды для стартового набора параметров это миграции Alembic (`0001`, `0002`); эта таблица их описывает.

## 4. Маппинг источников

### 4.1 rad.org.by: радиация (`rad_rss`)

Фид `https://rad.org.by/radiation.xml` (RSS), 42 поста.

| Поле контракта | Откуда |
|---|---|
| `station.name`, `station.external_id` | `<title>` (нормализованный; id в фиде нет); `kind = radiation_post` |
| `parameter` | всегда `gamma_dose_rate` |
| `value`, `unit` | `<rad>`, всегда `uSv/h` |
| `measured_at`, `period_kind` | `<pubDate>`, `instant` |
| `station.lat/lon` | в RSS нет (раздел 8) |
| `source_url` | `https://rad.org.by/monitoring/radiation.html` |

Регламент по тексту страницы: измерение 1 раз в сутки (погрешность не более 20%); если значение превышает среднемесячное за последние три месяца на 0,20 мкЗв/ч, наблюдения ведутся раз в час (приказ Минприроды от 30.04.2021 № 151-ОД). Повышенный фон в Брагине (зона Чернобыльской АЭС) это норма для этого поста, а не аномалия.

### 4.2 rad.org.by: воздух, доли ПДК (`rad_air_rss`)

Фид `https://rad.org.by/rss-air-avto.xml`, 19 постов (`kind = air_post`). Каждый `<item>` это один пост; в `<description>` значения текстом, а в самом item лежат числовые теги `<ingN>` вида `0.02 ПДК`.

| Поле контракта | Откуда |
|---|---|
| `station.external_id`, `name` | `<title>` нормализованный. `<guid>` это только номер в списке (`0`…`18`), кладём в `raw`, ключом не используем |
| `value`, `unit` | тег `<ingN>`, разбирать `split_value_unit()`; единица `ПДК → pdk_ratio`, `мкг/м3 → ug/m3` |
| `parameter` | по номеру тега, см. таблицу раздела 3 |
| `measured_at`, `period_kind` (газы) | `<pubDate>` (метки времени в фиде вида 17:20 и 17:00), `instant` |
| `measured_at`, `period_kind` (ТЧ-10, ТЧ-2,5) | `day`; начало суток, **предшествующих** дате `<pubDate>` (по тексту страницы: «средняя концентрация ТЧ представлена за предыдущие сутки»; проверить, см. раздел 8) |
| `source_url` | `https://rad.org.by/monitoring/air.html` |

Особенности:

- Сопоставление тегов с веществами сделано по совпадению значений в описании и в тегах: `ing2` серы диоксид, `ing4` углерод оксид, `ing5` азота диоксид, `ing6` азота оксид, `ing7` приземный озон, `ing46` О-ксилол, `ing200` ТЧ-10, `ing203` ТЧ-2,5.
- У разных постов разный набор веществ: четыре поста (Могилёв ул. Мовчанского, Минск ул. Тимирязева, Жлобин, Витебск) отдают только ТЧ, и их `pubDate` равен 00:00.
- В описании встречается `<0.01`, а в теге то же значение выглядит как `0`. Берём тег, исходный текст описания сохраняем в `raw`: нижняя граница чувствительности теряется (раздел 8).
- Данные на сайте обновляются автоматически, возможны пропуски и некорректные значения из-за сбоев оборудования (оговорка самой страницы).

### 4.3 rad.org.by: индекс качества воздуха (`rad_ikav_rss`)

Фид `https://rad.org.by/rss-air-ikv.xml`, 13 постов (`kind = air_post`), обновление ежечасно.

| Поле контракта | Откуда |
|---|---|
| `station.external_id` | `<guid>`, текстовый (напр. `Бобруйск`, `Минск, НПЗ №13`) |
| `station.name` | `<title>` |
| `parameter`, `value` | теги `<NO2>`, `<CO>`, `<SO2>`, `<O3>`: целое число, 1 = лучший класс; параметры `ikav_*` |
| `unit` | `class` |
| `measured_at`, `period_kind` | `<pubDate>` (на момент проверки 13:00 и 12:00), `instant` |
| `source_url` | `https://rad.org.by/monitoring/air.html` |

В описании то же значение текстом: `1` = «Очень хороший», `2` = «Хороший». Другие градации в просмотренных данных не встретились. Набор веществ у постов разный (на части нет `NO2` или `O3`), ТЧ в ИКАВ нет.

Названия постов в `rad_air_rss` и `rad_ikav_rss` пересекаются, но записаны по-разному (`Минск, ул.Радиальная, 50` и `Минск, НПЗ №13, ул.Радиальная, 50`), а `guid` устроены по-разному. Автоматического соответствия нет.

### 4.4 rad.org.by: классы качества поверхностных вод (`rad_water_rss`)

Фид `https://rad.org.by/rss-water.xml`, более 100 пунктов наблюдений (`kind = water_post`). Это не концентрации, а присвоенный раз в год **класс качества** за отчётный год (по тексту страницы статус присваивается один раз в год после обработки результатов).

| Поле контракта | Откуда |
|---|---|
| `station.external_id` | `<guid>`, числовой код пункта (например `523802354`) |
| `station.name` | `<title>`: «н.п.Ляцкие, вдхр.Беловежская Пуща (бассейн р.Зап.Буг)» |
| `parameter`, `value` | `<bio>` и `<chem>`: `parse_ru_class("2-ой класс") = 2`; параметры `water_class_bio` и `water_class_chem` |
| `unit` | `class` |
| `measured_at`, `period_kind` | 1 января года из `<description>` («(2025 год)»), `year`. `<pubDate>` это 31 декабря того же года, брать из него дату нельзя |
| `source_url` | `https://rad.org.by/monitoring/aqua.html` |

Ключ это именно `guid`: названия **повторяются** у разных пунктов (например, `г.Бобруйск, р.Березина` встречается с `guid` `531002910` и `531002911`, это разные створы). В просмотренных данных классы от 1 до 4.

### 4.5 rad.org.by: земли (почвы), резерв

Раздел `https://rad.org.by/monitoring/soil.html`. Машиночитаемого источника (RSS, JSON) мы не нашли; сами страницы раздела не открывались, ниже описание из верхнего раздела «Мониторинг».

- Сеть: 1056 пунктов в 34 городах, 88 пунктов в придорожных полосах (22 профиля на расстояниях 10, 25, 50 и 75 м от дороги), 90 пунктов на фоновых территориях.
- Периодичность: 1 раз в 5 лет на каждый пункт.
- Показатели: тяжёлые металлы (кадмий, цинк, свинец, медь, никель, хром, мышьяк, ртуть), сульфаты, нитраты, хлориды, нефтепродукты, бензо(а)пирен, полихлорированные бифенилы.

Для этого раздела в контракте уже есть `kind = soil_point`, а для периода пока нет значения: при появлении данных понадобится период в годах и, вероятно, расстояние и глубина как часть `sub_point`.

### 4.6 orsha-ecokarta (`orsha_ecokarta`)

Все ответы `https://orsha-ecokarta.gov.by/api/<имя>` имеют вид `{"nodes": [{"node": {...}}, ...]}` (Drupal Views). Эндпоинты делятся на справочники точек и данные.

| Эндпоинт | Записей* | Роль |
|---|---|---|
| `monitoring_aa_orsha` | 3 | станции, `kind = air_post` |
| `ala_place` | 4 | станции, `kind = industrial_site` |
| `lca_place` | 1 | станции, `kind = industrial_site` |
| `saemission-orsha` | 79 | станции, `kind = industrial_site` |
| `ac_air_place` | 0 | пока пустой; адаптер должен спокойно обрабатывать пустой список |
| `monitoring_aas_orsha` | 4186 | **измерения** (сутки), параметры `air_*` |
| `ac_air_place_substances` | 430 | **измерения** (месяц), параметры `emis_*` |
| `orsha-ap-substances` | 80 | вне MVP, см. раздел 8 |

\* на начало октября 2026.

**Порядок загрузки: сначала все справочники станций, потом измерения.** Измерение с неизвестным `field_geo_point` попадает в отчёт об ошибках.

#### Справочники точек → `StationIn`

| Поле контракта | Откуда |
|---|---|
| `external_id` | `Nid` (глобально уникален в Drupal; `field_point_id` повторяется между справочниками и ключом быть не может) |
| `name` | `title` |
| `address` | `nothing` (так поле названо во Views, к смыслу отношения не имеет) |
| `lat`, `lon` | `field_geolocation`, строка вида `"Широта: 54.48 Долгота: 30.39"`, разбирать `parse_ru_coords()` |
| `geo_quality` | `source` |

#### `monitoring_aas_orsha` → измерения воздуха

Одна запись это один пост за одни сутки, внутри несколько веществ.

| Поле контракта | Откуда |
|---|---|
| `station` | запись справочника с `Nid = field_geo_point` |
| `measured_at`, `period_kind` | `field_period` (`"1 октября 2026 г."`), `parse_ru_period()` → начало суток, `day` |
| вещества | поле `php`: **это JSON, упакованный в строку**, разбирать вторым `json.loads(node["php"])` |
| `parameter` | `field_pollutant_id` → таблица раздела 3 (префикс `air_`) |
| `value` | `field_average_concentration` |
| `unit` | `field_units_referencee` → `normalize_unit()` |
| `pdk` | `field_pdk` |
| `raw` | `{"record_nid": Nid, "field_source": ...}` |

Одна запись источника разворачивается в **несколько** `MeasurementIn` (по одному на вещество).

#### `ac_air_place_substances` → измерения у источников выбросов

| Поле контракта | Откуда |
|---|---|
| `station` | запись справочника с `Nid = field_geo_point` (например, `285` = ОАО Станкозавод «Красный борец» из `ala_place`) |
| `sub_point`, `sub_point_name` | `field_source` (напр. `325`), `title_2` (напр. `источник № 29`) |
| `measured_at`, `period_kind` | `field_period` (`"Июнь 2026"`) → начало месяца, `month` |
| вещества | `php` (двойной JSON, как выше) |
| `parameter` | `field_name_of_substance_id` → таблица раздела 3 (префикс `emis_`) |
| `value` | `field_actul_value` (опечатка в имени поля источника, оставляем как есть) |
| `unit` | `field_units_referencee` |
| `pdk` | `field_pdk` |

Пропускаем вещество, если `field_actul_value` равно `null`. Поля `field_local_analytical_avarage` и `field_analytical_actual_value` в просмотренных записях пустые; сохраняем их в `raw`. Справочники веществ у воздуха и у выбросов разные: CO это `2` в воздухе и `201` в выбросах, NO2 это `12` и `84`.

## 5. CSV (загрузка и выгрузка)

Один формат в обе стороны: выгруженный файл можно загрузить обратно.

- UTF-8, первая строка заголовок, разделитель запятая, десятичный разделитель точка. При выгрузке можно запросить `;` и BOM для русскоязычного Excel.
- Обязательные колонки: `source, station_external_id, station_name, lat, lon, parameter, value, unit, measured_at`. Остальные можно оставить пустыми (подставятся значения по умолчанию).
- Колонки в таком порядке:

```
source,station_external_id,station_name,station_kind,station_address,lat,lon,parameter,value,unit,measured_at,period_kind,pdk,sub_point,sub_point_name,source_url
```

Допустимые значения `station_kind` и `period_kind` перечислены в разделе 1.

Пример (координаты и значения иллюстративные):

```
orsha_ecokarta,1191,№3,air_post,ул. Пакгаузная,54.49,30.40,air_co,1340,ug/m3,2026-10-01T00:00:00+03:00,day,5000,,,
rad_rss,Брагин,Брагин,radiation_post,,51.79,30.25,gamma_dose_rate,0.47,uSv/h,2026-10-03T18:00:00+03:00,instant,,,,https://rad.org.by/monitoring/radiation.html
```

## 6. Схема БД (PostgreSQL)

Значения `kind`, `period_kind` и `unit` хранятся как текст, поэтому новые виды станций и периодов не требуют миграции схемы, только записи в справочнике параметров.

```sql
CREATE TABLE stations (
  id           BIGSERIAL PRIMARY KEY,
  source       TEXT NOT NULL,
  external_id  TEXT NOT NULL,
  name         TEXT NOT NULL,
  kind         TEXT NOT NULL DEFAULT 'other',
  address      TEXT,
  lat          DOUBLE PRECISION NOT NULL,
  lon          DOUBLE PRECISION NOT NULL,
  geo_quality  TEXT NOT NULL,
  UNIQUE (source, external_id)
);

CREATE TABLE parameters (
  code  TEXT PRIMARY KEY,
  name  TEXT NOT NULL,
  unit  TEXT NOT NULL
);

CREATE TABLE measurements (
  id              BIGSERIAL PRIMARY KEY,
  station_id      BIGINT NOT NULL REFERENCES stations(id),
  parameter       TEXT   NOT NULL REFERENCES parameters(code),
  sub_point       TEXT   NOT NULL DEFAULT '',
  sub_point_name  TEXT,
  value           NUMERIC NOT NULL,
  pdk             NUMERIC,
  period_kind     TEXT NOT NULL DEFAULT 'instant',
  measured_at     TIMESTAMPTZ NOT NULL,
  fetched_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  source_url      TEXT,
  upload_id       BIGINT,          -- NULL для автосбора
  raw             JSONB,
  UNIQUE (station_id, parameter, sub_point, measured_at)
);
CREATE INDEX ON measurements (parameter, measured_at);
```

Вставка: `INSERT ... ON CONFLICT (station_id, parameter, sub_point, measured_at) DO NOTHING`. Если окажется, что источник правит старые значения задним числом, заменить на `DO UPDATE SET value = EXCLUDED.value WHERE measurements.value IS DISTINCT FROM EXCLUDED.value`.

## 7. Интерфейс адаптера

```python
class SourceAdapter(Protocol):
    code: str
    def fetch(self) -> list[MeasurementIn]: ...
```

Адаптер ничего не знает про БД и планировщик: он достаёт данные и приводит их к `MeasurementIn`. Запись в БД делает общий сервис. Для orsha адаптер сам загружает справочники станций перед измерениями. `/api/monitoring_aas_orsha` отдаёт весь массив целиком (около 7 МБ): перед разбором стоит сравнить хэш или `ETag` ответа с прошлым и пропускать неизменившийся. RSS-фиды rad.org.by небольшие, но тоже отдают только текущий срез: истории нет, её накапливаем сами.

## 8. Открытые вопросы

**rad.org.by**

- **Координаты постов.** Ни в одном из четырёх фидов их нет. Они, скорее всего, лежат в данных виджетов карт (`/function/rad-map`, `/function/air-map`, `/function/air-ikv`, `/function/water-data?view=min`); эти страницы я не открывал, их нужно посмотреть в DevTools так же, как orsha. Запасной вариант: схемы сети наблюдений `/snob/*.html` или геокодинг по названию (`geo_quality = geocoded`).
- **Свежесть `rss-air-avto.xml`.** При проверке 7 октября 2026 в этом фиде стояла дата сборки 27 августа 2026, тогда как ИКАВ и воды показывали 7 октября. Либо фид давно не обновлялся, либо я получил кэшированную копию. Проверить в браузере до того, как строить на нём сбор.
- **Дата для ТЧ.** Страница говорит «за предыдущие сутки», а `pubDate` у таких постов 00:00 текущей даты. Мы принимаем «предыдущие сутки» буквально; подтвердить.
- **Нижняя граница чувствительности.** `<0.01` в описании превращается в `0` в теге: значение «меньше порога» неотличимо от настоящего нуля. Если это важно, добавить признак вроде `value_qualifier`.
- **Шкала ИКАВ и классов воды.** Мы видели ИКАВ 1–2 и классы воды 1–4; полные шкалы и их названия неизвестны. Для воды неизвестно, хранит ли фид предыдущие годы или только последний отчётный.
- **Устойчивость `guid` в `rad_ikav_rss`** (текстовые, привязаны к названию города и номеру поста) и в `rad_water_rss` (числовые, но один и тот же водный объект встречается с несколькими кодами).
- **Соответствие постов** между `rad_air_rss` и `rad_ikav_rss`: нужна таблица сопоставления, если захотим показывать их как один пост.
- **Почвы.** Нет проверенного машиночитаемого источника. Нужно открыть `soil.html` и `/snob/soil.html`.

**orsha-ecokarta**

- **Воды, почвы и радиация** на orsha-ecokarta не изучены.
- **`field_source`**: что обозначает (источник выбросов? протокол?). Предположение, что у одного предприятия несколько источников выбросов, различающихся по `field_source`, сделано по первой записи и должно быть проверено на остальных.
- **`мг/дм3` у выбросов в газе** выглядит необычно (значения до нескольких тысяч), как и `field_pdk` рядом: это может быть норматив для конкретного источника, а не ПДК воздуха. Пока храним как в источнике, не конвертируем.
- **Суточное значение воздуха**: поле называется `average_concentration`, вероятно, это среднее за сутки, но подтверждения нет.
- **`orsha-ap-substances`** (80 записей): это не измерения. Нет периода (`field_period` пуст), а `field_year_value` в сумме даёт `field_razr_val_v` (проверено на первой записи: 2.405 + 0.65 + 0.795 + 0.035 = 3.885), то есть, похоже, это разрешённые валовые выбросы по источнику. Единицы в данных не указаны. Решить: в MVP не грузим или кладём в отдельную таблицу.
- **Авторизация** для `/api/*` не нужна (в интерфейсе есть только кнопка входа, данные видны без неё); проверено на уровне интерфейса, а не явным запросом без cookies.
